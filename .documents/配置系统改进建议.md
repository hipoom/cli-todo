# 配置系统改进建议

## 1. 当前问题分析

### 1.1 架构层面问题

#### 1.1.1 配置层级混乱

**问题描述**：
- 当前配置分为三层（进程、App、Workspace），但各层配置的职责边界不够清晰
- 部分配置的存储位置选择不够合理，如 `current_style` 在 Workspace 级别，而 `styles` 在 App 级别
- 样式配置存在重复存储：`show.currentStyle` 和 `workspace.current_style` 都存储当前样式名称

**影响**：
- 开发者难以确定新配置应该放在哪一层
- 配置迁移和同步困难
- 容易出现配置不一致的问题

#### 1.1.2 配置访问方式不统一

**问题描述**：
- Workspace 级别配置有多种访问方式：
  - `Configs.show.xxx` - 便捷对象访问
  - `workspace.saveConfig()` / `workspace.queryConfig()` - 键值对访问
  - `workspace.getCurrentStyleName()` - 专用方法访问
- App 级别配置通过 `PersistentData` 对象访问
- 进程级别配置通过 `ProcessData` 对象访问

**影响**：
- 学习成本高，需要记忆多种访问方式
- 代码风格不统一
- 维护困难

### 1.2 代码层面问题

#### 1.2.1 配置类设计不一致

**问题描述**：
- `Configs`、`Show`、`Window`、`Launch` 等对象使用 object 单例模式
- `Styles` 使用 object 单例但包含可变状态 `styles`
- `StyleStorage`、`TextMappingStorage` 使用 object 单例提供静态方法
- `AutoLabelRule` 是数据类，存储在 Workspace 数据库中

**影响**：
- 代码风格不统一
- 部分配置需要手动加载，部分自动加载
- 状态管理复杂

#### 1.2.2 缺乏类型安全

**问题描述**：
- `ConfigGroup` 使用字符串键名访问配置
- 颜色值使用字符串格式 "R,G,B"，需要手动解析
- 数据库键名使用字符串常量，容易拼写错误

**影响**：
- 运行时错误风险高
- IDE 无法提供代码补全
- 重构困难

#### 1.2.3 配置变更通知缺失

**问题描述**：
- 配置变更后没有通知机制
- 部分配置变更后需要手动调用 `storeCurrentConfigs()` 保存
- 配置变更后相关功能不会自动更新

**影响**：
- 配置变更可能不生效
- 需要重启应用才能看到效果
- 用户体验差

### 1.3 文档层面问题

#### 1.3.1 配置文档缺失

**问题描述**：
- 缺乏统一的配置文档
- 配置项说明分散在代码注释中
- 新开发者需要阅读源码才能了解配置系统

**影响**：
- 学习成本高
- 容易误用配置

#### 1.3.2 配置迁移指南缺失

**问题描述**：
- 版本升级时配置格式可能变化
- 没有配置迁移机制
- 没有配置兼容性说明

**影响**：
- 版本升级可能导致配置丢失
- 用户需要手动修复配置

## 2. 改进建议

### 2.1 高优先级改进（建议立即实施）

#### 2.1.1 统一配置访问接口

**建议**：
创建统一的配置访问接口 `ConfigManager`，提供一致的访问方式。

```kotlin
// 建议的配置访问接口
interface ConfigManager {
    // 获取配置
    fun <T> get(key: ConfigKey<T>): T
    
    // 设置配置
    fun <T> set(key: ConfigKey<T>, value: T)
    
    // 监听配置变更
    fun <T> observe(key: ConfigKey<T>, observer: (T) -> Unit)
}

// 类型安全的配置键
class ConfigKey<T>(
    val name: String,
    val defaultValue: T,
    val scope: ConfigScope
)

enum class ConfigScope {
    PROCESS, APP, WORKSPACE
}
```

**优先级**：高
**工作量**：中等
**收益**：提高代码可维护性，降低学习成本

#### 2.1.2 消除配置重复存储

**建议**：
- 将 `current_style` 统一存储在 App 级别（因为样式是 App 级别配置）
- 删除 `show.currentStyle` 配置项
- 清理 `workspace.getCurrentStyleName()` 和 `workspace.setCurrentStyleName()` 方法

**优先级**：高
**工作量**：小
**收益**：消除配置不一致风险

#### 2.1.3 添加颜色类型支持

**建议**：
创建 `ColorConfig` 类型，替代字符串格式的颜色配置。

```kotlin
// 建议的颜色配置类型
data class ColorConfig(
    val r: Int,
    val g: Int,
    val b: Int
) {
    fun toColor(): Color = Colors.Bits24.createForeground(r, g, b)
    
    companion object {
        fun fromString(str: String): ColorConfig? {
            val parts = str.split(",").mapNotNull { it.trim().toIntOrNull() }
            if (parts.size != 3) return null
            return ColorConfig(parts[0], parts[1], parts[2])
        }
    }
}
```

**优先级**：高
**工作量**：小
**收益**：类型安全，减少解析错误

### 2.2 中优先级改进（建议近期实施）

#### 2.2.1 实现配置变更通知机制

**建议**：
引入观察者模式，支持配置变更通知。

```kotlin
// 建议的配置观察者接口
interface ConfigObserver {
    fun onConfigChanged(key: String, oldValue: Any?, newValue: Any?)
}

// 在 ConfigManager 中添加
class ConfigManager {
    private val observers = mutableListOf<ConfigObserver>()
    
    fun addObserver(observer: ConfigObserver) {
        observers.add(observer)
    }
    
    fun removeObserver(observer: ConfigObserver) {
        observers.remove(observer)
    }
    
    private fun notifyObservers(key: String, oldValue: Any?, newValue: Any?) {
        observers.forEach { it.onConfigChanged(key, oldValue, newValue) }
    }
}
```

**优先级**：中
**工作量**：中等
**收益**：配置变更实时生效，提升用户体验

#### 2.2.2 统一配置存储策略

**建议**：
明确各层配置的职责和存储策略：

| 层级 | 职责 | 存储方式 | 适用配置 |
|------|------|----------|----------|
| 进程级别 | 运行时临时状态 | 内存 | 当前工作空间、命令前缀 |
| App 级别 | 跨工作空间共享配置 | 数据库 | 样式、文本映射、当前工作空间别名 |
| Workspace 级别 | 工作空间特定配置 | 文件/数据库 | 显示配置、模板、自动标签规则 |

**优先级**：中
**工作量**：小
**收益**：职责清晰，便于维护

#### 2.2.3 添加配置验证机制

**建议**：
在配置保存前进行验证，确保配置值合法。

```kotlin
// 建议的配置验证接口
interface ConfigValidator<T> {
    fun validate(value: T): Boolean
    fun getErrorMessage(value: T): String
}

// 示例：颜色验证器
class ColorValidator : ConfigValidator<ColorConfig> {
    override fun validate(value: ColorConfig): Boolean {
        return value.r in 0..255 && value.g in 0..255 && value.b in 0..255
    }
    
    override fun getErrorMessage(value: ColorConfig): String {
        return "颜色值必须在 0-255 范围内"
    }
}
```

**优先级**：中
**工作量**：中等
**收益**：防止非法配置值，提高系统稳定性

### 2.3 低优先级改进（建议长期规划）

#### 2.3.1 引入配置版本管理

**建议**：
为配置文件添加版本号，支持配置迁移。

```kotlin
// 建议的配置版本管理
data class ConfigFile(
    val version: Int,
    val data: ConfigGroup
)

// 配置迁移接口
interface ConfigMigration {
    val fromVersion: Int
    val toVersion: Int
    fun migrate(config: ConfigGroup): ConfigGroup
}
```

**优先级**：低
**工作量**：大
**收益**：支持平滑升级，防止配置丢失

#### 2.3.2 实现配置导入导出

**建议**：
支持配置的导入导出功能，方便用户备份和迁移配置。

```kotlin
// 建议的配置导入导出接口
interface ConfigExporter {
    fun export(workspace: WorkspaceContext): String
    fun import(workspace: WorkspaceContext, json: String): Boolean
}
```

**优先级**：低
**工作量**：中等
**收益**：方便用户备份和迁移配置

#### 2.3.3 添加配置加密支持

**建议**：
对敏感配置（如 API Key）提供加密存储支持。

**优先级**：低
**工作量**：大
**收益**：提高安全性

## 4. 重构建议

### 4.1 配置类重构

**当前结构**：
```
Config-ext.kt
├── Configs (object)
│   ├── Window (object)
│   ├── Show (object)
│   │   ├── CommentStyle (object)
│   │   ├── Status (object)
│   │   └── Icon (object)
│   └── Launch (object)
├── Focus (object)
└── BooleanField (class)
```

**建议结构**：
```
config/
├── ConfigManager.kt          // 统一配置管理器
├── ConfigKey.kt              // 类型安全的配置键
├── ConfigScope.kt            // 配置作用域枚举
├── validators/               // 配置验证器
│   ├── ConfigValidator.kt
│   ├── ColorValidator.kt
│   └── BooleanValidator.kt
├── types/                    // 配置类型
│   ├── ColorConfig.kt
│   └── StyleConfig.kt
├── storage/                  // 配置存储
│   ├── ProcessConfigStorage.kt
│   ├── AppConfigStorage.kt
│   └── WorkspaceConfigStorage.kt
└── keys/                     // 配置键定义
    ├── ShowConfigKeys.kt
    ├── WindowConfigKeys.kt
    └── LaunchConfigKeys.kt
```

### 4.2 迁移步骤

1. **第一阶段**：创建新的配置管理架构，保持向后兼容
2. **第二阶段**：逐步迁移现有配置到新架构
3. **第三阶段**：删除旧的配置访问方式
4. **第四阶段**：添加配置迁移和验证功能

## 5. 结论

当前配置系统存在架构混乱、访问方式不统一、类型不安全等问题。建议按照优先级逐步实施改进，首先解决高优先级问题，然后逐步完善配置系统。重构过程中需要保持向后兼容，确保现有功能不受影响。
